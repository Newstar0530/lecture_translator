## 實際 API 測試觀察到的現象

- **12 分鐘內發生 3 次 silent stall**（第 32、143、193 秒），恢復要 3–5 秒重連；第 3 條連線連上後仍然沒有文字，要再重連一次才恢復。
- **第一條連線一開始就沒有文字**（32 秒後判定卡死），和 2026-10-20 14:11 那堂課的第一條連線一樣。
- **同一段音訊重播時，在相近的位置又卡住**：原本那堂課在這段錄音的約第 66–289 秒卡住（連續重連失敗），重播時在約第 112–198 秒卡住。課後辨識在 105–200 秒辨識出 159 個字，代表那段確實有人在講話。這暗示卡住可能和音訊內容或連線狀態有關，不完全是隨機的伺服器故障（目前只有一個例子，是假設，不是結論）。如果成立，同一段錄音可以重複重現灰色故障，可用來比較偵測策略。
- **取消競態在實際 API 下 3 次重連都沒有發生**（orphaned 0），但每次拆連線都有 1 段已交給 SDK、`send_audio()` 沒有返回（`handed − send_returned = 3`，正好是 3 次重連），那 3 段（各 100 毫秒）很可能沒有送到伺服器。
- 伺服器回報的 `target_streaming_delay_ms` 是 `None`（沒有告訴我們實際用的延遲）。
- 翻譯延遲：63 句全部成功，從斷句到譯文完成 p50 1.01 秒、p95 1.58 秒、最大 3.17 秒。
